## 6. Authentication & Authorization

**Login/signup flow:**
- `accounts/forms.py` defines `SignupForm` (extends `UserCreationForm`, adds `email` and `role` fields) and `LoginForm` (extends `AuthenticationForm`, no customization)
- `accounts/views.py`:
  - `signup_view` — creates user, logs them in immediately, redirects to `dashboard`
  - `login_view` — standard Django auth, redirects to `dashboard`
  - `logout_view` — logs out, redirects to `login`
  - `dashboard_view` — decorated with `@login_required`

**Protected routes:** All `meetings/views.py` view functions (`create_meeting`, `join_meeting`, `meeting_room`, `end_meeting`, `leave_meeting`) are decorated with `@login_required`. Unauthenticated users are redirected to Django's default login URL.

**WebSocket authentication:** `core/asgi.py` wraps the WebSocket router in `AuthMiddlewareStack`, so `self.scope['user']` is available inside `MeetingConsumer` and reflects the logged-in Django session user. This is how chat messages and join/leave events are attributed to the correct username.

**Role-based access logic:** Minimal. The `role` field exists on `User` (`host` / `participant` choices) and is displayed on the dashboard, but the actual host/participant distinction in meetings is determined separately and independently by `meeting.host == request.user` (i.e., whoever created the Meeting row is the host of THAT meeting — this is NOT the same as the global `User.role` field). This is an important architectural nuance: **a user's account-level `role` field and their per-meeting host status are two separate, unconnected concepts.** This may confuse the next developer if not clarified — the `User.role` field is currently cosmetic/unused for actual permission checks.

## 8. API Documentation

There is **no formal REST API** (despite `djangorestframework` being installed) — all interaction is via standard Django views returning HTML, plus one WebSocket endpoint. No `serializers.py` or DRF `APIView`/`ViewSet` classes exist anywhere in the project.

### HTTP Routes

| Method | URL | View | Auth required | Description |
|---|---|---|---|---|
| GET/POST | `/accounts/signup/` | `signup_view` | No | Render/process signup form |
| GET/POST | `/accounts/login/` | `login_view` | No | Render/process login form |
| GET | `/accounts/logout/` | `logout_view` | Yes | Logs out, redirects to login |
| GET | `/accounts/dashboard/` | `dashboard_view` | Yes | Dashboard page |
| GET/POST | `/meetings/create/` | `create_meeting` | Yes | Creates Meeting + Participant, redirects to room |
| GET/POST | `/meetings/join/` | `join_meeting` | Yes | Looks up Meeting by room_code, creates Participant, redirects to room |
| GET | `/meetings/room/<room_code>/` | `meeting_room` | Yes | Renders the room page with participants + chat history |
| GET | `/meetings/end/<room_code>/` | `end_meeting` | Yes (host only via queryset filter) | Marks meeting inactive, deactivates all participants |
| GET | `/meetings/leave/<room_code>/` | `leave_meeting` | Yes | Deactivates that user's Participant row |
| GET | `/admin/` | Django admin | Yes (staff) | Default Django admin, models not registered |
| GET | `/` | `TemplateView` | No | Landing page |
| GET | `/static/...` | static() | No | Static files served via Django in dev mode |

### WebSocket Endpoint

`ws(s)://<host>/ws/meeting/<room_code>/` → handled by `meetings.consumers.MeetingConsumer`

**Client → Server message types:**
```json
{ "type": "signal", "target": "<channel_name>", "signal": { ... SDP/ICE data ... } }
{ "type": "chat", "message": "<text>" }
```

**Server → Client message types:**
```json
{ "type": "existing-members", "members": [ { "channel": "...", "user": "..." }, ... ] }
{ "type": "user-joined", "user": "...", "channel": "..." }
{ "type": "user-left", "user": "...", "channel": "..." }
{ "type": "signal", "sender_channel": "...", "sender": "...", "signal": { ... }, "target": "..." }
{ "type": "chat", "message": "...", "sender": "..." }
```

No authentication token is passed explicitly over the WebSocket — auth relies on the Django session cookie being valid at connection time (via `AuthMiddlewareStack`).

## 11. Known Issues & Bugs

1. **Redis incompatibility (RESOLVED via workaround, not a true fix):** The installed Redis for Windows (version 3.0.504) does not support the `BZPOPMIN` command required by `channels-redis`. This caused WebSocket connections to immediately disconnect with `redis.exceptions.ResponseError: unknown command 'BZPOPMIN'`. **Workaround applied:** switched `CHANNEL_LAYERS` to `InMemoryChannelLayer`, bypassing Redis entirely. **This is NOT production-ready** — a real Redis 6.2+ instance (e.g., via Docker, WSL, or a managed Redis service) is needed for any multi-process deployment.

2. **CDN tracking-prevention blocking SimplePeer.js:** Microsoft Edge's "Tracking Prevention" feature blocked loading `simplepeer.min.js` from `unpkg.com`, breaking all WebRTC functionality with no clear error initially. **Fixed** by downloading the library and self-hosting it at `static/js/simplepeer.min.js`.

3. **STATIC_URL missing leading slash:** `STATIC_URL = 'static/'` (without leading `/`) caused static files to be served with wrong MIME type (`text/html` instead of `application/javascript`) through ngrok, causing `Refused to execute script` errors. **Fixed** by changing to `STATIC_URL = '/static/'` and adding explicit `static()` pattern to `core/urls.py`.

4. **base.html layout breaking the room page:** The shared `templates/accounts/base.html` has `body { display:flex; justify-content:center; align-items:center }` styling meant for centered auth-form cards. This broke the full-screen video grid layout when `room.html` extended it. **Fixed** by creating a separate minimal `templates/meetings/base_room.html` with no centering, and pointing `room.html` to extend that instead.

5. **Peer connection "initiator" logic bug (RESOLVED):** Initially, both new and existing peers tried to initiate the WebRTC connection symmetrically, causing duplicate/failed peer connections and participants not seeing each other (always showing "1 participant" on both ends, or duplicate video tiles after refresh). **Fixed** by establishing a clear rule: existing members always initiate (`initiator: true`) toward a new joiner; the new joiner responds as non-initiator (`initiator: false`) when receiving a `user-joined` event. Also added cleanup logic (`createPeer` now destroys any pre-existing peer for that channel before creating a new one) to prevent duplicate tiles on refresh/rejoin.

6. **Same-device WebRTC testing limitation:** Two browser tabs on the same physical machine cannot properly test two-camera video calling (only one process can access the webcam at a time) — this is a hardware limitation, not a code bug. Testing requires either two physical devices or careful single-camera/audio-only testing.

7. **Mobile screen-share unsupported:** `getDisplayMedia()` is not available on Android/iOS browsers. This is **by design**, not a bug — the screen-share button is deliberately disabled on mobile via a `navigator.userAgent` check.

8. **ngrok free-tier URL instability:** Every ngrok restart generates a brand-new random subdomain (e.g., `maturing-supplier-undertow.ngrok-free.app` → later `.dev`), requiring `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` to be manually updated in `settings.py` each time ngrok is restarted. This is a recurring friction point during dev/testing and will need a more permanent solution (paid ngrok static domain, or real deployment) going forward.

9. **Chat feature — UNVERIFIED:** As noted above, this was actively being implemented in the final part of this conversation. The next developer should treat chat as "code written, not confirmed working" rather than "done."

10. **No automated tests:** `tests.py` files exist in each app but are empty Django boilerplate — zero test coverage currently.

11. **Daphne must be manually restarted after every settings.py/consumers.py/routing.py change** — there is no auto-reload in this dev setup (unlike `manage.py runserver`'s autoreloader), which has been a repeated source of "why isn't my fix working" confusion during the session.

## 13. Final Handover Summary

This is a Django-based real-time video conferencing platform built incrementally over 3 of 12 planned weeks by a 3-person intern team. **Working features:** user auth with custom roles, meeting room creation/joining via unique codes, full peer-to-peer WebRTC video/audio calling with mute/camera/screen-share controls, and live participant tracking — all powered by Django Channels (WebSocket) for signaling and SimplePeer.js (self-hosted, not CDN-loaded) for the actual WebRTC handshake. The app currently runs via **Daphne** (not `manage.py runserver` — this is critical, WebSockets won't work otherwise) using an **in-memory channel layer** (a temporary workaround after the installed Windows Redis build proved incompatible with `channels-redis`). Real-time text chat (model + WebSocket handler + UI) was the most recently written code and **needs verification** before being considered complete — check that migrations ran and test live message exchange across two devices first.

The architecture pattern to preserve going forward: each new real-time feature (chat done; transcription/translation next) should follow the same pattern already established — extend `MeetingConsumer.receive()` to handle a new `type` of WebSocket message, broadcast it via `channel_layer.group_send()`, and optionally persist it to a new Django model mirroring `ChatMessage`. The video/signaling logic in `room.html`'s inline JavaScript should NOT need to change for these additions — it's self-contained and stable now.

**Before doing anything else**, the next developer/AI should: (1) confirm the chat feature actually works by running `migrate` and testing live, (2) be aware that `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` currently contain stale/temporary ngrok URLs that will need refreshing for continued cross-device testing, and (3) understand that production-readiness items (PostgreSQL, real Redis, deployment config) have been deliberately deferred and are NOT yet started — current state is dev-only on a single Windows machine.
